"跨库 join = 0" 是按**目标分库**口径统计的：同一条 SQL 里出现两个以上库的表就算跨库。脚本按 `TABLE_DB` 映射判定（identity / order / payment / catalog / learning / ops）。

|---|---|---|

| 其中业务读路径 | 8 | **0**（归零） |

1. `commerce:CatalogRepository`——原六表一 SQL，跨 order/catalog/learning/identity（P3 商店）；
2. `course:SeriesRepository`——原四查询分别 join catalog/identity/learning（P4 播放）；
3. `learning:LearningProgressRepository` / `learning:PlaybackLogRepository`——原 join 内容表与权益表做归属校验（P5 学习域）；

5. `course:TeacherContentRepository`——原 join 用户表取教师昵称（P6 教师端）。

**业务跨库多表 SQL 已归零。** 仅剩 1 个白名单类（支付单比对查询）。

本轮消除：

6. `operations:AdminOrderMapper`——订单页不再 join 用户表：按用户名搜索先由 `identity.api.AccountDirectory.searchIds` 得到 userId 集合，下单人姓名/账号由 `profiles` 批量补齐（P7 运营订单）；
7. `operations:AdminUserMapper`——用户管理页整表迁出：分页/关键字/角色过滤走 `identity.api.AccountQuery`，权益数走 `EntitlementQuery.activeCountsByUser`，分配/回收走 `EntitlementAdmin`，课程选项走 `CatalogQuery.publishedOptions`。该 Mapper 与 XML 已删除（P7 运营用户）；
8. `operations:AdminOrderMapper`（查询部分）——订单分页/异常订单查询搬进 `AdminOrderOperations` 契约，operations 不再持有订单表 SQL（P8）；
9. `platform:AlertLogRepository`——播放统计查询下沉为 `learning.api.PlaybackStatsQuery`，内核不再读播放日志表（P8）。

**跨模块表（有效口径）已归零。** 唯一例外是 `com.wherelee.base.bootstrap`：种子/装配代码横跨多张业务表，属于组合根职责，已在扫描器 `COMPOSER_MODULES` 登记并在基线 `composer_modules` 中固化；它不计入业务模块越权，但会随生产 profile 收口一起处理。

| 库 | 表 | 保护等级 |
|---|---|---|
| `identity_db` | `t_user`、`t_teacher_invitation`、`t_role`、`t_permission`、`t_user_role`、`t_role_permission`、`t_tenant`、`t_app` | 高 |
| `payment_db` | `t_payment_order`、`t_payment_attempt`、`t_payment_event`、`t_refund`、`t_payment_outbox`、`t_recon_task`、`t_recon_diff`、`t_channel_bill` | **最高**（独立实例） |
| `order_db` | `t_order`、`t_order_item`、`t_order_status_log` | 高 |
| `catalog_db` | `t_series`、`t_series_chapter`、`t_series_video`、`t_price`、`t_media_asset` | 中 |
| `learning_db` | `t_entitlement`（原 `t_student_series`）、`t_learning_progress`、`t_playback_log`（按月分区） | 中 |
| `ops_db` | `t_admin_audit_log`、`t_alert_log`、`t_compensation_task` | 中 |

> 表的物理拆分（`t_student_series` → `t_entitlement`、内容与定价分离、媒体资产独立）在 P1/P2 迁移中完成，本文只锁定边界。

**所有权规则**

1. 每张表只有一个 owner 库，owner 之外的模块**不得直接读写**；
2. 跨域读取通过 `api` 接口（进程内）或服务接口（拆分后），禁止 join；
3. 唯一例外是同域内的多表 join（如 identity 的邀请表 join 用户表）——在同一 owner 库内允许；
4. 每个库独立账号，应用账号无 DDL 权限。

## 4. 收口方案（按类）

目标是把「跨模块表 8 → 0、多表 SQL 类 9 → 0」，每一类都有明确改法。

### 4.1 `CatalogRepository`（commerce/order）— ✅ 已收口（2026-11-18）

原实现：一条 SQL join `t_series` / `t_series_chapter` / `t_series_video` / `t_user` / `t_student_series` / `t_order` 六张表。

现实现（三段拼装，零跨域 SQL）：

| 数据 | 来源 | 边界 |
|---|---|---|
| 商品信息（标题/摘要/价格/章节视频计数/教师名） | `course.api.CatalogQuery` | 课程域自己查自己的表；教师昵称走 `identity.api.AccountDirectory` 批量接口 |
| 是否已购 | `EntitlementRepository.activeSeriesIds` | commerce 模块内（权益表） |
| 进行中订单 | `OrderRepository.findActiveOrders` | commerce 模块内（订单表） |

代码落点：`course/api/CatalogQuery` + `course/catalog/CatalogQueryService`、`identity/api/AccountDirectory` + `identity/user/AccountDirectoryService`、重写后的 `commerce/order/CatalogRepository`。

代价：3 次查询代替 1 次 join；收益：商品展示不再依赖课程表结构，跨域从 SQL 级降为接口级。

回归证据：`CatalogCompositionIntegrationTest`（2 个用例，验证行为完全等价：已购标记、进行中订单、教师名、章节/视频计数、可购买校验）。

连带收益：`t_series` 访问模块 5→4、`t_series_chapter` 4→3、`t_series_video` 4→3、`t_user` 5→4。

### 4.2 `SeriesRepository`（course/series）— ✅ 已收口（2026-11-18）

原实现四个查询分别 join `t_student_series` / `t_series` / `t_user` / `t_series_chapter` / `t_series_video` / `t_learning_progress`（跨 catalog + identity + learning 三域）。

现实现（契约拼装，零跨域 SQL）：

| 数据 | 来源 | 边界 |
|---|---|---|
| 课程/章节/视频元信息 | `course.api.CatalogQuery`（新增 `findByIds` / `findChapters` / `findVideoRefs` / `findVideo`） | 课程域自读自表 |
| 有没有权益 | `commerce.api.EntitlementQuery`（新增） | 权益域单表 |
| 看到哪了 / 完成数 | `learning.api.ProgressQuery`（新增，批量） | 学习域单表 |

固定 4 次查询（权益/课程/视频/进度）换掉一条跨三域 SQL；学习空间不再依赖其他域任何表结构。

**顺带修了一个正确性缺陷**：原可播放校验只看权益，课程下架或视频未就绪时已购学员仍能拿到播放地址。现在要求「权益 + 课程 PUBLISHED + 视频 READY」三者同时满足，回归用例 `LearningSpaceReadModelIntegrationTest` 覆盖。

连带收益：`t_learning_progress` 访问模块 2→1（跨模块表从 8 降到 7）。

### 4.3 `AdminSeriesMapper` / `TeacherContentRepository`（course）

- `AdminSeriesMapper` 的列表统计改为「分页查目录 → 批量补权益数/学员数」，不再在 SQL 里 join；
- `TeacherContentRepository` 去掉 `t_user` join，教师名走冗余或 `identity.api`；
- `TeacherInvitationMapper` 的 `t_user` join 属同库同域，**保留**。

### 4.4 `LearningProgressRepository` / `PlaybackLogRepository`（learning）

- 权益校验统一走 `commerce.api.EntitlementQuery`（同时修掉现在两套口径：`PlaybackLogRepository` 不校验 `valid_to` 而 `LearningProgressRepository` 校验的 bug）；
- 内容标题改为冗余或 `course.api` 查询；进度表只保留 `video_id` 自身字段。

### 4.4 `LearningProgressRepository` / `PlaybackLogRepository`（learning）— ✅ 已收口（2026-11-18）

原实现两个查询都 join `t_series_video` / `t_series_chapter`（内容域）和 `t_student_series`（权益域）来判断"这个视频属于哪门课、这个用户有没有权限"。

现实现：`course.api.CatalogQuery.findVideo(videoId)` 拿视频上下文（含 seriesId、时长、媒体状态、课程状态）+ `commerce.api.EntitlementQuery.hasActive(userId, seriesId)` 判权限；两个仓库退化为单表访问。

**ArchUnit 规则同步演进**：原规则禁止 learning 依赖任何其他业务模块；现在改为「可以依赖其他模块的 `api` 契约，禁止依赖其实现包」，identity/operations 仍完全禁止。同时把 ArchUnit 分析范围限定到主代码（`ImportOption.DoNotIncludeTests`），避免测试类继承关系被误判为架构违规。

**顺带修的第二个正确性缺陷**：原播放日志校验不查 `valid_to`、进度写入查，导致权益过期用户"能写播放日志、写不了进度"。现在两者共用同一套权益口径，`LearningAccessIntegrationTest` 覆盖。

### 4.5 `AdminSeriesMapper` / `TeacherContentRepository`（course）— ✅ 已收口（2026-11-18）

- 富有语义的「教师名」改由 `identity.api.AccountDirectory` 批量解析；按教师名搜索时，先由身份域 `searchIds` 得到 teacherId 列表，课程库只按 id 过滤（不在课程 SQL 里 join 用户表）；
- 「已分配学员数」改由 `commerce.api.EntitlementQuery.activeStudentCounts` 批量统计，课程列表分页后一次补齐，不做 N+1；
- 教师端系列详情不再 join `t_user`，昵称由服务层从身份契约取。

连带收益：`t_user` 的访问方从 4 个模块降到 **3 个**（bootstrap / identity / operations），课程域彻底不再碰用户表。

### 4.6 `AdminOrderMapper` / `AdminUserMapper`（operations）— ✅ 已收口（2026-11-18）

- 订单管理：新增身份域批量资料接口 `AccountDirectory.profiles`；关键字搜索下沉身份域（`searchIds`），订单库只按 `user_id IN (...)` 过滤；下单人用户名/昵称在分页后批量补齐。
- 用户管理：新增 `identity.api.AccountQuery`（分页 + 关键字 + 角色状态过滤）与 `commerce.api.EntitlementAdmin`（分配/回收权益）；`AdminUserMapper` 与 `AdminUserMapper.xml` 整体删除，运营端不再有任何用户表/权益表 SQL。
- 回归：`AdminConsoleIntegrationTest` 覆盖用户分页带权益数、分配/回收闭环、订单页下单人信息补齐。


- `AdminUserMapper` 直写 `t_student_series` → 改为 `commerce.api.EntitlementAdmin.grant/revoke`；
- `AdminOrderMapper` join `t_user` → 批量调 `identity.api.UserAccountOperations.require/find`。

### 4.7 `DataInitializer`（原 platform/config）— ✅ 已收口（2026-11-18）

示例数据初始化横跨 5 张业务表，却住在内核 `platform` 下，属于数据级 R1 违规（platform 反向依赖业务表）。

已迁到 `com.wherelee.base.bootstrap` 包（独立装配单元，不归属任何业务模块）。效果：`platform` 从 `t_series` / `t_series_chapter` / `t_series_video` / `t_student_series` / `t_user` 的访问方里消失。

遗留：该初始化器当前是 `@Profile("!integration")`，生产环境也会执行；`bootstrap` 目录下已有安全顾虑记录（默认口令），是否改为仅 dev/profile 控制属于上线前收口项，不在 A 期范围。

### 4.7 `PaymentOrderShadowRepository`（多表 SQL 白名单）

P1 新增的比对查询会 join `t_order` 与 `t_payment_order`。这是**审计/校验用途**，不是业务读路径，因此在基线里显式登记为允许的多表类（`allow_multi_table` 之外的 `multi_table_classes` 清单）。

纪律：只有比对/对账/归档这类"读出来核对"的组件可以登记；任何业务链路上的多表 SQL 不允许走白名单。

## 7. 多租户隔离（A 期收口，2026-11-18）

- **字段**：V16 给全部业务表加 `tenant_id`（默认 0），安全相关唯一键前缀化（`(tenant_id, username)`、`(tenant_id, order_no)` 等），并加租户维度索引。
- **上下文**：`TenantContext`（ThreadLocal）由 `JwtAuthFilter` 从 JWT claim `tid` 写入，请求结束清理；业务代码不得从请求参数取租户。
- **拦截器**：`TenantAwareJdbcTemplate` 替换默认 JdbcTemplate，`TenantSqlRewriter` 对单表 SQL 自动注入 `tenant_id`，跨表/子查询语句必须手写租户条件，否则直接抛错（`app.tenant.enforce=true`）。
- **MyBatis 语句**：三个 Mapper（课程治理、邀请、播放日志）显式带 `tenant_id` 参数。
- **证据**：`TenantIsolationIntegrationTest` 3 个用例——订单按租户隔离（写入自动打标、跨租户查不到）、商品目录隔离、权益隔离；全量集成测试 33 通过。
